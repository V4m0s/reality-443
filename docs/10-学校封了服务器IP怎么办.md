# 学校把服务器 IP 封了怎么办（Cloudflare 前置）

> 这一篇是**进阶救命篇**。只有一种情况需要看：
> **昨天还能用，今天所有网站都打不开，连服务器都连不上。**
>
> 如果你现在只是"抖音打不开"，那是 [09-校园网特殊配置](09-校园网特殊配置.md) 的问题，不用看这篇。

---

## 一、先判断：到底是学校封的，还是服务器挂了

这两件事的症状一模一样，但修法完全不同。花 3 分钟测一下，别瞎改。

在**电脑上**依次执行（Windows 用 PowerShell，Mac 用终端）：

```bash
# 1. 能不能连上服务器的 443
Test-NetConnection 203.0.113.45 -Port 443      # Windows
nc -vz 203.0.113.45 443                        # Mac

# 2. 能不能连上别的境外 IP（对照）
Test-NetConnection github.com -Port 443
```

对照结果：

| 你的 IP | 别的境外站 | 结论 |
|---|---|---|
| 超时 | 正常 | **学校封了你的 IP** → 看这篇 |
| 超时 | 也超时 | 整个网络有问题 → 先查校园网本身 |
| 能连上 | 正常 | IP 没封，是别的问题 → 看 [06-出问题了怎么办](06-出问题了怎么办.md) |

再看一眼服务器活没活着（能连上 22 端口就说明活着）：

```bash
ssh -i 你的密钥 ubuntu@203.0.113.45 "uptime; systemctl is-active xray"
```

> 实测记录：被封的时候，`443` 超时、`22` 也超时，但**同机房的另外一个 AWS IP 也是超时**，
> 而 GitHub / Cloudflare 都正常——这就是"按 IP 封"，不是"你这台机器坏了"。

---

## 二、为什么用 Cloudflare，而不是换个 IP 就完事

换 IP 只要 2 分钟，但**下一轮还会被封**（我们实测：一个 IP 只活了 1 天）。

换成 Cloudflare 前置之后，学校看到的是"你在访问一个普通的 Cloudflare 网站"，
封 IP 变得没有意义——因为封的是 Cloudflare，而学校不敢封 Cloudflare（那等于断掉半个互联网）。

### 两种接法的实测对比（同一个校园网、同一台服务器）

| 接法 | 首屏延迟 | 下载速度 |
|---|---|---|
| 让 Cloudflare 直接回源到 `2053` 端口 | 4.1s | **0.14 MB/s** ❌ |
| **用 Cloudflare 隧道，走 443** | 1.2s | **3.87 MB/s** ✅ |

差 27 倍。**所以必须用隧道，不要用"改端口回源"的偷懒办法。**

---

## 三、你需要准备什么

| 东西 | 说明 |
|---|---|
| 一个域名 | 免费也行（见下），买的话约 20 元/年 |
| 一个 Cloudflare 账号 | 免费，邮箱注册 |
| 服务器能 SSH 登录 | 你已经有了 |

**免费域名**（能用，但每年要手动续期，忘了会被回收）：

- `us.kg` / `dpdns.org` —— DigitalPlat 提供，注册时选"外部名称服务器"
- `eu.org` —— 老牌免费域名，但审核要等几天到几周

> 打算长期用、或者想写进教程给别人看，**建议花 20 块买个 `.top` / `.xyz`**。
> 免费域名最大的坑不是钱，是"哪天没了你都不知道"。

---

## 四、第一步：把域名接到 Cloudflare

1. 打开 <https://dash.cloudflare.com> → 注册 / 登录
2. **Add a site** → 输入你的域名（比如 `myline.dpdns.org`）→ 选 **Free**
3. Cloudflare 会给你两个 NS 地址，长这样：

   ```
   keira.ns.cloudflare.com
   carmelo.ns.cloudflare.com
   ```

4. 回到你**买域名的地方**，把 NS 改成这两个

   - 买的是 `us.kg` / `dpdns.org`：注册时选**「外部名称服务器」**，把 NS1 / NS2 填进去
   - 买的是阿里云/腾讯云：找"DNS 修改" / "自定义 DNS"，填这两个

5. 回 Cloudflare 点 **Check nameservers now**，等状态变成 **Active**（5 分钟到 2 小时）

✅ **检查点**：Cloudflare 首页顶部显示 `Active`

> **踩过的坑**：改 NS 属于"安全设置"，有些注册商会要求你**重新登录 + 验证邮箱**才允许改。
> 如果改 NS 时页面返回一段 JSON（`reauthentication_required`），就是没验证，重新登录走一遍验证就行。

---

## 五、第二步：给服务器加一个"Cloudflare 专用入口"

原来的 443 是给 REALITY 用的，不能动。我们另开一个**只监听本机**的 WebSocket 入口：

```bash
sudo cp /usr/local/etc/xray/config.json /usr/local/etc/xray/config.json.bak-cf

sudo python3 - <<'PY'
import json
p = "/usr/local/etc/xray/config.json"
c = json.load(open(p))
uuid = c["inbounds"][0]["settings"]["clients"][0]["id"]     # 沿用原来的 UUID
ws = {
  "tag": "ws-in", "listen": "127.0.0.1", "port": 8080, "protocol": "vless",
  "settings": {"clients": [{"id": uuid, "flow": ""}], "decryption": "none"},
  "streamSettings": {"network": "ws", "security": "none", "wsSettings": {"path": "/ws"}}
}
c["inbounds"] = [i for i in c["inbounds"] if i.get("tag") != "ws-in"] + [ws]
json.dump(c, open(p, "w"), indent=2)
print("done")
PY

sudo xray -test -c /usr/local/etc/xray/config.json     # 显示 Configuration OK 再往下
sudo systemctl restart xray
```

✅ **检查点**：`ss -ltn | grep 8080` 能看到 `127.0.0.1:8080`

> 为什么只监听 `127.0.0.1`？因为**它不需要被外面访问**——流量是 Cloudflare 主动送进来的，
> 外面看不到这个端口，也就不可能被封。

## 六、第三步：建隧道（命令行方式，不用 Zero Trust）

> **为什么不用网页版 Zero Trust？**
> 因为它会让你选套餐，而且**即使选免费版也可能强制绑定支付方式**。
> 命令行方式完全绕开这一步，也不花一分钱。

### 6.1 装 cloudflared

```bash
curl -fsSL -o /tmp/cf.deb https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64.deb
sudo dpkg -i /tmp/cf.deb
cloudflared --version
```

### 6.2 登录（会给你一个授权链接）

```bash
cloudflared tunnel login
```

它会打印一条很长的链接，形如：

```
https://dash.cloudflare.com/argotunnel?aud=&callback=https%3A%2F%2Flogin.cloudflareaccess.org%2F...
```

**把这条链接复制到浏览器打开** → 登录 → 选择你的域名 → 点 **Authorize**。

成功后服务器上会出现证书：`ls ~/.cloudflared/cert.pem`

> 如果 SSH 会话中途断了、或者跑在网页终端里，用这条命令让它脱离会话运行：
>
> ```bash
> sudo systemd-run --unit=cflogin --collect --property=User=ubuntu \
>   --setenv=HOME=/home/ubuntu /usr/local/bin/cloudflared tunnel login
> sudo journalctl -u cflogin -n 30 | grep -o 'https://dash[^ ]*'
> ```

### 6.3 创建隧道

```bash
cloudflared tunnel create tokyo-443
```

输出里会有一行：

```
Created tunnel tokyo-443 with id a1b2c3d4-0000-1111-2222-333344445555
```

**记下这个 ID**，后面要用。

### 6.4 绑定域名

```bash
cloudflared tunnel route dns tokyo-443 你的域名
```

> ⚠️ **这里是最容易翻车的一步**，见第九节第 1 个坑。

---

## 七、第四步：把隧道装成开机自启的服务

```bash
TID=<你的隧道ID>

sudo mkdir -p /etc/cloudflared
sudo cp ~/.cloudflared/$TID.json /etc/cloudflared/

sudo tee /etc/cloudflared/config.yml >/dev/null <<EOF
tunnel: $TID
credentials-file: /etc/cloudflared/$TID.json
no-autoupdate: true
ingress:
  - hostname: 你的域名
    service: http://127.0.0.1:8080
  - service: http_status:404
EOF

sudo cloudflared service install
sudo systemctl enable --now cloudflared
systemctl is-active cloudflared        # 应为 active
```

日志里看到这样的行就对了：

```
INF Registered tunnel connection connIndex=0 location=nrt01 protocol=quic
```

`nrt` = 东京，说明隧道接的是就近节点。

✅ **检查点**

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://你的域名/
```

返回 **404** 就对了（404 是 Xray 对非 `/ws` 路径的正常回应，说明请求已经穿过隧道到达服务器）。
如果返回 **1033**，说明隧道没绑上这个域名；返回 **502**，说明隧道连不到本机 8080。

## 八、第五步：客户端换成隧道节点

和直连节点相比，只有三处不同：**地址换成域名、传输换成 ws、走 tls**。

```
vless://<你的UUID>@你的域名:443
  ?encryption=none
  &security=tls
  &sni=你的域名
  &fp=chrome
  &type=ws
  &path=%2Fws
  &host=你的域名
  #东京-CF
```

（上面为了方便阅读分了行，实际使用时连成一行。）

在你用的客户端里：

| 客户端 | 怎么加 |
|---|---|
| Windows / Xray | 直接加到 `config.json`，见第十节 |
| iOS / Streisand | 扫二维码，或从剪贴板导入 |
| Android / v2rayNG | 扫二维码，或从剪贴板导入 |

✅ **检查点**：打开 <https://ipify.org>，显示的是你服务器的 IP，而不是你家的 IP。

## 九、我们踩过的六个坑（你大概率也会踩）

### 坑 1：学校 DNS 不解析 `*.cfargotunnel.com`

**症状**：电脑上 `nslookup 你的域名 8.8.8.8` 有结果，但用学校 DNS 查是**空的**；
换手机流量一切正常。

**原因**：隧道绑定后会生成一条 CNAME 指向 `<隧道ID>.cfargotunnel.com`，
学校 DNS 把这个域名拉黑了，于是整条链路解析不出来。

**修法**：把隧道绑到**根域名**（`myline.dpdns.org`），不要用子域名（`vpn.myline.dpdns.org`）。
根域名是普通 A 记录，Cloudflare 会自动"压平"，学校 DNS 看到的就是普通 IP。

```bash
cloudflared tunnel route dns tokyo-443 你的根域名
```

如果报 "record already exists"，先去 Cloudflare 的 DNS 页面把原来的 A 记录删掉，再执行。

### 坑 2：想让 Cloudflare 直接回源到非 443 端口

**别做。** 实测 `2053` 回源只有 0.14 MB/s，隧道走 443 有 3.87 MB/s，差 27 倍。
Cloudflare 对非标端口的转发走的是完全不同的链路。

### 坑 3：Zero Trust 让你绑支付方式

命令行 `cloudflared tunnel login` 完全绕开它（第六节）。

### 坑 4：IPv6 优先导致超时

校园网、热点常常没有可用的 IPv6，但域名会返回 AAAA。客户端优先试 IPv6 就挂死。

**修法**：给代理出站加

```json
"domainStrategy": "UseIPv4"
```

### 坑 5：`sudo cloudflared service install` 后服务起不来

八成是 `config.yml` 里的 `credentials-file` 路径不对。
用绝对路径：`/etc/cloudflared/<隧道ID>.json`，并确认文件存在。

### 坑 6：改完配置重启 xray，SSH 立刻断

如果你是通过这台服务器自己的代理连 SSH（很常见），**重启 xray 会把你的 SSH 一起掐断**。

**修法**：延时重启，让命令先返回：

```bash
sudo nohup sh -c 'sleep 3; systemctl restart xray' >/dev/null 2>&1 &
```

## 十、进阶：让客户端在两条线路之间自动切换

到这里你手上有两条路：

- **REALITY 直连**：没被封时最快
- **Cloudflare 隧道**：被封时照样能用

问题是你不知道该用哪条。让客户端每 30 秒测一次，自动挑快的：

```json
{
  "observatory": {
    "subjectSelector": ["reality", "cf"],
    "probeUrl": "https://www.google.com/generate_204",
    "probeInterval": "30s",
    "enableConcurrency": true
  },
  "routing": {
    "domainStrategy": "IPIfNonMatch",
    "balancers": [
      { "tag": "auto", "selector": ["reality", "cf"], "strategy": { "type": "leastPing" } }
    ],
    "rules": [
      { "type": "field", "ip": ["geoip:private"], "outboundTag": "direct" },
      { "type": "field", "domain": ["geosite:cn"], "outboundTag": "direct" },
      { "type": "field", "ip": ["geoip:cn"], "outboundTag": "direct" },
      { "type": "field", "network": "tcp,udp", "balancerTag": "auto" }
    ]
  }
}
```

两个必须注意的细节：

**① 规则里调用均衡器，字段名是 `balancerTag`，不是 `outboundTag`。**

写成 `"outboundTag": "auto"` 不会报错，但**每个请求都会瞬间失败**（0.006 秒返回 000），
我第一次就栽在这里，查了半小时。

**② 探针地址别用 `gstatic.com`。**

实测它在 Cloudflare 那条线上会超时，导致均衡器误判"这条线死了"，永远不选它。
用 `https://www.google.com/generate_204`。

### 实测效果

| 场景 | 客户端自动选 | 结果 |
|---|---|---|
| 学校没封 IP | REALITY 直连 | google 204 / 0.28s，下载 3.5–6 MB/s |
| 学校封了 IP | Cloudflare 隧道 | google 204 / 1.3s，下载 3.8 MB/s |

两条都挂着，客户端自己选，你不用管。

---

## 十一、最后一个提醒

这套方案让**你的线路**更难被封，但它不会让流量"隐身"：

- 学校仍然能看到"你在持续和 Cloudflare 通信"
- Cloudflare 能看到你的域名和源站
- 用自己的域名给很多人共用，被滥用的风险由你承担

**自己用、给朋友用，够。** 别拿它做成公开的机场——
那会把"一个学生自己搭条线"的小事，变成"一个可以被一锅端的服务"。

```

  4. cloudflared tunnel create tokyo-443
  5. cloudflared tunnel route dns tokyo-443 根域名
  6. /etc/cloudflared/config.yml  → ingress 指向 127.0.0.1:8080
  7. cloudflared service install && systemctl enable --now cloudflared
  8. 客户端换成 ws + tls 节点

验证：curl https://你的域名/  →  404（正常）
      开 ipify.org          →  显示服务器 IP
```
